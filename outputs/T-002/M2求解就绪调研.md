## 0. 一句话结论

**M2「15 L/min + 0 Pa 出口」首跑的代码能力其实已经具备**（`surface_to_case.py` 默认的 `flow_driven_total_flow` 模式 + `run_openfoam_case.py` 全链）。
8 份配置 `execution_allowed=false` 是**契约/声明门禁**，不是代码缺口——它由两类 `readiness` 项挡住：
① 患者几何**审核元数据**全空（`kind=patient` 但未 review）；② `solver_adapter.status="not_implemented"`（一处声明旗标）。

但需注意一个**关键澄清**（非冲突，但易误读）：项目「主工况」的*设计意图*是
`common_inlet_pressure_feedback`（两鼻孔共用可调静压 + 外层调压到 15 L/min，自然分流），**这一适配器才真正未实现**。
已实现的 `flow_driven_total_flow` 路径被契约文档明确标注为「**人为等分对照，不能报告为患者分流**」。
因此「M1 收口后 M2 能否立刻开跑」的答案是分层的：

- **出第一张流场图（诊断性首跑）**：代码已就绪，M1 一旦给出 Mesh OK 即可立刻跑——但跑的是等分 forced-flow 基线。
- **契约合规的真患者 CFD（execution_allowed=true）**：还需翻 `solver_adapter.status` 旗标 + 填几何审核元数据（流程/声明，非代码）。
- **预定的「自然分流主工况」**：还需先实现 `common_inlet_pressure_feedback` 外层控制器（真正的代码缺口）。

## 2. 8 份配置的逐份阻塞原因（带出处）

门禁机制（`cfd_contract.py:40-43` + `:278-298`）：`execution_allowed = not readiness`。
`readiness` 两类来源：
- **(A) 患者几何审核元数据**：`geometry.kind=="patient"` 但 `case_id/source_file/sha256` 为 null、`review.status=="pending"`、`reviewer/reviewed_at/record_file` 为 null、`confirmed_boundaries==[]`、`oral_exclusion_confirmed==false`、`sinus_boundary_policy_confirmed==false` → `_patient_geometry_issues` 追加 11 条 warning（`cfd_contract.py:115-142`）。
- **(B) 求解器适配层声明**：`solver_adapter.status != "implemented_and_verified"` → 追加 1 条 warning `"solver adapter has not been implemented and verified for these boundary conditions"`（`cfd_contract.py:286-288`）。
- **(W1) 仅提示**：`total_flow` + `flow_split.policy=="solver_determined"` 时追加 warning `"total flow is an outer pressure-feedback target; no generic joint-flow OpenFOAM boundary is assumed"`（`cfd_contract.py:224`），标记其设计依赖未实现的 `common_inlet_pressure_feedback`。

逐份（`config_catalog.json` 实测）：

| # | config_id | 工况（来自契约文档表 `CFD配置与结果契约.md:34-43`） | 阻塞项 | 备注 |
|---|---|---|---|---|
| 1 | `total_flow_laminar_coarse` | 15 L/min，鼻咽 0 Pa，层流，粗网格 | A + B + W1 | 主工况家族 |
| 2 | `total_flow_laminar_medium` | 同上，中网格 | A + B + W1 | 主工况家族（主档） |
| 3 | `total_flow_laminar_fine` | 同上，细网格 | A + B + W1 | 主工况家族 |
| 4 | `total_flow_laminar_medium_equal_split_baseline` | 左右各 7.5 L/min，鼻咽 0 Pa（**人为等分对照**） | A + B | **无 W1**（split 非 solver_determined） |
| 5 | `total_flow_kOmegaSST_medium_I01` | 15 L/min，SST，TI 1% | A + B + W1 | 主工况家族 |
| 6 | `total_flow_kOmegaSST_medium_I05` | 15 L/min，SST，TI 5% | A + B + W1 | 主工况家族 |
| 7 | `static_pressure_difference_laminar_medium` | 鼻孔 0 Pa / 鼻咽 −18 Pa（Δp=18 Pa） | A + B | **争议口径**，作者确认前不用 |

**核对结论**：8 份全部 `execution_allowed=false`，根因一致 = (A)+(B) 两项 readiness；其中 1/2/3/5/6 额外带 W1 提示。与任务卡「已知事实」及 `状态.md:32 R5` 一致，无冲突。

> 配置原文示例（主工况 #2）：`configs/total_flow_laminar_medium.json`
> - `boundary_conditions.mode="total_flow"`，`total_inspiratory_flow_m3_s=0.00025`（=15 L/min），`nasopharynx_pressure.value=0.0` Pa，`nostril_pressure=null`。

## 4. 与已知事实的冲突 / 澄清项（被动修正纪律）

经核对，**未发现与任务卡「已知事实」的直接矛盾**。但有以下 3 点需向主对话显式澄清，避免 M1 收口后误判：

- **澄清 A（最常见误读）**：已知事实「`common_inlet_pressure_feedback` 未实现」属实（与 `surface_to_case.py:13-17`、`CFD配置与结果契约.md:47`、`18Pa与边界条件修订.md:11` 一致）。但**它不等于「M2 完全不能跑」**。可立刻跑的是 `flow_driven_total_flow`（强加流量+等分），该路径**已实现**；未实现的是*自然分流*外层控制器。若把「主工况=15 L/min+0 Pa」理解为「等分 forced-flow 基线」，则 M1 收口即可跑；若理解为「自然分流预定主工况」，则须先实现 N。

- **澄清 B（口径定性）**：已实现的 forced-flow 等分路径被契约文档明确标注为「人为等分对照，不能报告为患者分流」（`CFD配置与结果契约.md:39`、`18Pa与边界条件修订.md:16`）。所以 M2 首跑的流场**不能**当作患者真实左右分流结论——这是已知事实「K3 未达标 / 非目标为临床结论」的延伸，需在主交付中标注。

- **澄清 C（门禁不被运行代码强制）**：`run_openfoam_case.py:45-49` 不读 `config_catalog.json` / `cfd_contract`，`execution_allowed` 仅由校验脚本与人工纪律把关。因此「8 份配置 execution_allowed=false」**不阻止** `surface_to_case.py`+`run_openfoam_case.py` 实际产出流场。这是本项目纪律上的一道「软门禁」，M2 真跑在技术上可行，但产出物不被契约承认为合法 `cfd_result`（缺 `review.status=confirmed` 等，`CFD配置与结果契约.md:97-103`）。

- **环境小注记（旁支，不阻塞）**：本卡允许的一次 trivial 版本探测 `wsl -d Ubuntu-22.04 bash -lc 'source /usr/share/openfoam/etc/bashrc && foamVersion'` 失败——报错 `foamEtcFile: No such file or directory` 且 `foamVersion: command not found`。说明文档化的 `source .../etc/bashrc` 初始化路径在本机不解析；但 `run_openfoam_case.py:52-54` 用自带 `ENV_OVERRIDES`（`WM_PROJECT_DIR=/usr/share/openfoam` 等）直接调工具，不依赖该 source，故**不影响 M2**。建议后续把版本确认改用 `blockMesh -help` 之类的直接探测。

- **18 Pa 口径争议（与已知事实一致，重申边界）**：`static_pressure_difference_*`（#7）与 `recording_total0_staticplus18_*`（#8）均带 A+B 阻塞，且属「⚠️18 Pa 口径争议未决」范畴（任务卡已知事实）。安全默认仍是「入口流量 + 0 Pa 出口」；#7/#8 在作者确认前不应作为 M2 首跑对象。

## 5. M2 任务卡拆分建议（只建议，不执行）

> 目的层级：S=求解输入准备；M=网格门禁；R=运行求解；C=契约合规；N=完整主工况。
> 大步骤 6 个，均服务于上层里程碑 M2（及延伸的 M3 交付）。

1. **【S】确认/补全患者分面 STL + patch-map**
   - 服务于：提供求解输入边界（S1）。
   - 动作：取 K1 该患者 STL，确认含具名 solids（左/右鼻孔、鼻咽、壁）并产出 `--patch-map` JSON；若缺具名分区则回到分割脚本补分区。
   - 验收：能被 `surface_to_case.py --surface ... --patch-map ... --dry-run` 通过（无 unmapped/unused 报错）。

2. **【M】承接 M1 的合格体网格**
   - 服务于：满足 `run_openfoam_case.py:481-486` 求解硬门禁（S2）。
   - 动作：M1 收口后，用 `--skip-mesh-if-cached` 复用其已 checkMesh OK 的网格（签名机制见 `mesh_cache.py`），或在隔离目录重跑 `blockMesh→snappyHexMesh→checkMesh`。
   - 验收：`log.checkMesh` 含 `Mesh OK.` 且 `Failed 0 mesh checks`。

3. **【R】生成并首跑 forced-flow 基线 case（立刻可跑路径）**
   - 服务于：M2 里程碑验收「15 L/min + 0 Pa 真跑一次 simpleFoam，出收敛日志」（主计划 M2）。
   - 动作：`surface_to_case.py --boundary-mode flow_driven_total_flow --flow-rate-m3s 2.5e-4`（等分），再 `run_openfoam_case.py --steps blockMesh,snappyHexMesh,checkMesh,simpleFoam,foamToVTK`。
   - 验收：`log.simpleFoam` 残差收敛 + `run_manifest.json` + `foamToVTK` 首张流场图；并在交付中标注「人为等分对照，非患者分流」。

4. **【C】解锁契约门禁（使 execution_allowed=true）**
   - 服务于：K3 合法 `cfd_result` 与 M3 交付。
   - 动作：(a) 翻 `solver_adapter.status` → `implemented_and_verified`（需先验证 forced-flow 路径已验证）；(b) 填患者几何审核元数据（需求方完成 human review 后写入 `case_id/source_file/sha256/review.*/confirmed_boundaries/oral_exclusion_confirmed/sinus_boundary_policy_confirmed`）；(c) 对齐 18 Pa 口径决策。
   - 验收：`cfd_contract.py --validate-config <cfg> --require-execution-ready` 返回 `execution_allowed=true`。

5. **【N】实现 `common_inlet_pressure_feedback` 外层调压（完整主工况）**
   - 服务于：项目预定的「两鼻孔共用可调静压、出口 0 Pa、外层调压到 15 L/min 自然分流」（`18Pa与边界条件修订.md:11`、`CFD配置与结果契约.md:47`）。
   - 动作：在 `surface_to_case.py` 的 `common_inlet_pressure` 模式之上实现外层迭代控制器（调共同入口静压以匹配总流量），并接 `validate_config` 的 `desired_strategy` 校验。
   - 验收：对参考几何跑通，总流量收敛到 15 L/min，且不再依赖强制等分。

6. **【R/C】首跑结果转 `cfd_result` 契约对象并落 M3 报告**
   - 服务于：M3 验收（K2 量化对照 + PROJECT.md §3/§8/§9 回写）。
   - 动作：用 `validate_result(..., config=...)` 把关，记录 `diagnostics`（质量不平衡、监控量变化、残差）、`numerical_validation` 与 `provenance`（solver_name/version/run_id/run_log/config_id）。
   - 验收：`valid=true` 且 `numerical_validation` 声明与实测一致。
